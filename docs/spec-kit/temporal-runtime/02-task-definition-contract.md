# Task Definition Contract

**Date**: 2026-04-08
**Status**: Proposed implementation reference

## Purpose

A task definition expresses launch intent.

It answers:

- what should run
- whether the run is ad hoc, delayed-once, or recurring
- whether the run targets an existing BEADS issue or materializes a new one

It does not define workflow semantics after launch.

## Contract

```ts
type TaskDefinition = {
  version: 1;
  taskDefinitionId: string;
  name: string;
  mode: "ad_hoc" | "scheduled_once" | "recurring";
  materialization: TaskMaterialization;
  runtimePolicy?: RuntimePolicy;
  metadata?: Record<string, string>;
};

type TaskMaterialization =
  | {
      kind: "existing_beads_issue";
      beadsId: string;
    }
  | {
      kind: "create_beads_issue";
      issueType: "bug" | "feature" | "task" | "epic" | "chore" | "decision";
      titleTemplate: string;
      descriptionTemplateRef?: string;
      labels?: string[];
      priority?: 0 | 1 | 2 | 3 | 4;
      parentBeadsId?: string;
    };

type RuntimePolicy = {
  maxRuntimeHours?: number;
  maxRetryAttempts?: number;
  allowOvernight?: boolean;
  summaryRequired?: boolean;
};

type AdHocLaunchRequest = {
  version: 1;
  taskDefinitionId: string;
  initiatedAt: string;
  initiatedBy: "operator";
  runId?: string;
  runtimeSkeleton?: {
    mode: "complete" | "sleep_until";
    sleepUntil?: string;
    reason?: string;
  };
};

type LaunchRecord = {
  version: 1;
  runId: string;
  taskDefinitionId: string;
  triggerType: "ad_hoc" | "scheduled_once" | "recurring";
  scheduleId?: string;
  initiatedAt: string;
  initiatedBy: "operator" | "schedule";
  materialization: {
    sourceKind: "existing_beads_issue" | "create_beads_issue";
    resolvedBeadsId: string;
    created: boolean;
    createRequest?: {
      issueType: "bug" | "feature" | "task" | "epic" | "chore" | "decision";
      title: string;
      description?: string;
      labels?: string[];
      priority?: 0 | 1 | 2 | 3 | 4;
      parentBeadsId?: string;
    };
  };
  runtimeStart?: {
    mode: "immediate" | "delayed_once";
    startDelayMs?: number;
    scheduledFor?: string;
  };
  workflowInput: IssueWorkflowInput;
};
```

## Field Semantics

### `taskDefinitionId`

Stable identifier for the launch intent.

This is not the BEADS issue id and not the Temporal workflow id.

### `mode`

- `ad_hoc`: launched immediately by an operator
- `scheduled_once`: launched later exactly once
- `recurring`: launched on a recurring cadence

### `materialization`

Defines how the run maps to BEADS.

Allowed forms:

- use an existing BEADS issue or epic
- create a new BEADS issue or epic from a template at run start

Materialization happens before the Temporal workflow starts.

The workflow input contract should receive one concrete BEADS id, not a deferred materialization instruction.

## Materialization Rules

### Existing BEADS Issue

Use this when:

- the task already exists in BEADS
- the operator wants to run or resume that task

### Create New BEADS Issue

Use this when:

- the task is recurring
- the run should create a fresh task each time
- the run is generated from a template or automation policy

Required fields are intentionally aligned to `bd create` so the launch layer can materialize the target without hidden assumptions:

- `issueType`: BEADS issue type to create
- `titleTemplate`: deterministic title template
- `descriptionTemplateRef`: optional repo-relative markdown/text file used as the issue description
- `labels`, `priority`, `parentBeadsId`: optional explicit BEADS creation inputs

Supported Step 2 render tokens for `titleTemplate`:

- `{run_id}`
- `{task_definition_id}`
- `{yyyy}`
- `{mm}`
- `{dd}`

The same tokens may be used inside `descriptionTemplateRef` contents when a description template is rendered.

For Step 2, date tokens are derived from `initiatedAt` in UTC so ad hoc rendering remains deterministic across machines. Schedule-aware local-time rendering is deferred to the schedule phase.

### Step 2 Restricted Profile

Step 2 only implements the ad hoc launch entrypoint.

Supported in Step 2:

- loading and validating task definitions from repo-local JSON files
- `mode: "ad_hoc"` task definitions
- ad hoc launch requests initiated by an operator
- explicit materialization to an existing BEADS issue or a newly created BEADS issue
- launch-record emission that captures how the run mapped to a concrete BEADS target

Deferred until later steps:

- scheduler-driven execution of `scheduled_once` and `recurring` definitions
- recurring title/body token expansion beyond the small token set above
- policy-driven mutation of BEADS after workflow start

## Ad Hoc Launch Request

The Step 2 ad hoc entrypoint should accept a small launch request rather than raw workflow input.

Rules:

- `taskDefinitionId` identifies the repo-local task definition to load
- `initiatedBy` is `operator`
- `runId` may be supplied by the caller or generated by the launch layer
- `runtimeSkeleton` is a temporary pass-through only because the Step 1 workflow still needs it

The launch layer validates this request, resolves materialization, and only then produces `IssueWorkflowInput`.

## Launch Record

Each ad hoc run should write one launch record before or at workflow start.

Purpose:

- make materialization auditable
- explain which BEADS id was selected or created
- prove that create-new and existing-target launches normalize to the same workflow input contract

The launch record is a derived audit artifact for launch-time decisions.

It is not workflow truth and it is not a substitute for Temporal execution history.

Starting in Step 3, the same launch-record shape is also used for schedule-triggered runs. In those cases:

- `triggerType` reflects the schedule-triggered entrypoint
- `scheduleId` identifies the schedule definition that triggered the run
- `initiatedBy` is `schedule`
- `runtimeStart` may describe delayed-start intent such as `scheduledFor` and `startDelayMs`

## Invariants

1. A task definition must not contain workflow phase state.
2. A task definition must not contain runtime sleep state.
3. A task definition must not replace BEADS as task truth.
4. Materialization must be explicit: target existing BEADS state or create new BEADS state.
5. Create-new materialization must contain enough explicit data to call `bd create` deterministically.
6. A task definition must not require the workflow to infer how BEADS materialization should happen.

## Example: Ad Hoc Existing Issue

```json
{
  "version": 1,
  "taskDefinitionId": "taskdef-auth-fix-now",
  "name": "Auth bug fix now",
  "mode": "ad_hoc",
  "materialization": {
    "kind": "existing_beads_issue",
    "beadsId": "bd-1234"
  },
  "runtimePolicy": {
    "maxRuntimeHours": 8,
    "maxRetryAttempts": 3,
    "allowOvernight": true,
    "summaryRequired": true
  }
}
```

## Example: Recurring Fresh Issue

```json
{
  "version": 1,
  "taskDefinitionId": "taskdef-weekly-knowledge-maintenance",
  "name": "Weekly knowledge maintenance",
  "mode": "recurring",
  "materialization": {
    "kind": "create_beads_issue",
    "issueType": "task",
    "titleTemplate": "Weekly knowledge maintenance - {yyyy}-{mm}-{dd}",
    "descriptionTemplateRef": "templates/runtime/weekly-knowledge-maintenance.md",
    "labels": ["automation", "knowledge", "weekly"],
    "priority": 3
  },
  "runtimePolicy": {
    "maxRuntimeHours": 4,
    "maxRetryAttempts": 2,
    "allowOvernight": true,
    "summaryRequired": true
  }
}
```

## Recommended Storage

Suggested repo-local location:

```text
.metaswarm/runtime/task-definitions/<task-definition-id>.json
```

This is configuration and launch intent.

It is not workflow truth.

Step 2 should also persist a launch record per run:

```text
.metaswarm/runtime/launches/<run-id>.json
```

That launch record is an audit trail for task-definition resolution and BEADS materialization. It is not a replacement for BEADS or Temporal execution history.
